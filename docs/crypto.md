# Cryptography decisions (architecture spec v4, WP0)

## Library choice

| Side | Library | Version | Why |
|---|---|---|---|
| Browser (doctor, staff, patient) | **WebCrypto** (built into the browser) | the browser's own | No new dependency to download or audit, it runs in every current browser, and keys can be held as non-extractable `CryptoKey` objects. The spec allows the WebCrypto suite (section 5.2). |
| Python (institution adapters, platform, tests) | **`cryptography`** | 50.0.2, already installed through `pyjwt[crypto]` 2.10.1 | Vetted, already in both images, so no new download. Same algorithms as the browser, so both sides interoperate. |

No cryptography is written by hand: every primitive is a library call. libsodium (X25519, sealed boxes) was the alternative. It was not chosen because the browser would need a new package (`libsodium-wrappers`), and WebCrypto's X25519 support is still uneven across browsers.

## The suite, `refx-p256-v1`

| Purpose | Algorithm | Parameters |
|---|---|---|
| Content encryption | **AES-256-GCM** | Fresh random 96-bit nonce per encryption; 128-bit tag; associated data (AAD) `refx/v1|item|<referral reference>|<item_id>|<key_version>` binds the ciphertext to its referral, item and key version |
| Data key (DEK) | 256-bit random AES key | One per record batch: one source institution's answer, one doctor's own items, or the receiving hospital's added records. Its `key_version` is the batch id. |
| Wrapping a DEK to a recipient | **ECIES on P-256**: ephemeral ECDH P-256, then HKDF-SHA-256, then AES-256-GCM | HKDF salt = the ephemeral public key (SPKI DER); HKDF info = `refx/v1|wrap|<context>`; AAD = the same context. The context names the referral, batch and recipient key id, so a wrapped key cannot be moved to another referral or recipient. |
| Signatures | **ECDSA P-256 with SHA-256** | Raw `r‖s` (64 bytes, IEEE P1363), as WebCrypto produces. Python converts to and from DER. |
| Machine-to-machine assertions | **ES256 JWT** (ECDSA P-256) | Short-lived (5 minutes), with `jti` replay protection |
| Private-key backup and unlock | **PBKDF2-HMAC-SHA-256**, 600,000 iterations, 16-byte salt, then AES-256-GCM | Argon2id is preferred by the spec but is not in WebCrypto. PBKDF2 at this iteration count is the spec's allowed alternative. |
| Hashes (manifest, ciphertext) | SHA-256 | Hex encoded |

**Encodings:**
- **Public keys:** SPKI DER, base64.
- **Signatures and nonces:** base64url without padding.
- **Ciphertext:** base64.
- **Signed JSON:** canonical JSON (keys sorted, no spaces, UTF-8) of the object without its `signature` field.

## Keys and where they live

| Key | Generated by | Private part held by | Public part |
|---|---|---|---|
| Hospital signing key (ECDSA) | Each institution's adapter, on first start | The adapter's key store (its own database, encrypted with the adapter's `ADAPTER_KEY_SECRET`) | Exchanged directly between adapters at onboarding (`scripts/onboard_participants.py`) and registered with the platform |
| Platform signing key (ECDSA, ES256) | The platform, on first start | The platform's key store | Published at `/.well-known/jwks.json`; adapters pin it at onboarding |
| Doctor encryption key (ECDH) and signing key (ECDSA) | The doctor's browser | The doctor's device: IndexedDB, as a passphrase-encrypted PKCS#8 blob, unlocked into non-extractable keys for the session | Directory entry, signed by the doctor's hospital |
| Department group key (ECDH) | The receiving hospital's adapter | The adapter (the hospital's own system holds a member copy by policy), and each member doctor, wrapped to their encryption key | Directory entry, signed by the hospital |
| Patient key (ECDH and ECDSA) | The patient's browser (patient portal) | The patient's device | Directory entry, signed by the platform when the logged-in patient registers it |

**The deliberate trust points**, stated in `docs/security-model.md`:
- Each hospital's adapter holds its departments' group keys, so the hospital's own system can read referrals sent to its departments. The hospital is the data controller for its patients' care.
- Patient key entries are signed by the platform. A malicious platform could therefore register a false patient key.
- The browser application is served by the platform. A malicious platform could ship altered client code.

## Unlock UX

Logging in (Keycloak) proves who you are. The device key decrypts the data. A doctor sets a passphrase once, on first use on a device. The keys are generated in the browser, and only the public keys leave the device: they are signed by the hospital and published. On later visits, the doctor types the passphrase to unlock the keys for that session. Backup: the encrypted key blob can be downloaded as a file and restored on another device with the passphrase.
